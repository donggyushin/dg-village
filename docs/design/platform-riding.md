# 발판(platform) 탑승 설계 — 여객선부터

2026-11-13 오너와 Claude 가 논의해서 정한 설계다. 첫 대상은 정원 선착장과 Sacred isle 사이의 여객선(`Art/Ferry`, id `ferry_willow`)이다. 메시지 형식은 [`../protocol.md`](../protocol.md)가 기준이다.

## 목표

1. 유저가 배에 걸어서 탄다.
2. 배에 탄 유저가 배를 출발시킨다.
3. 배가 섬으로 가고, 유저는 섬에서 내리거나 그대로 다시 돌아간다.
4. 같은 씬의 모든 유저가 배와 배 위의 유저를 같은 위치에 본다.

## 용어

- **발판(platform)**: 정해진 경로로 스스로 움직이고, 유저가 그 위를 걸어 다니는 것. 배, 엘리베이터, 열차.
- **조종하는 탈것**: 유저가 직접 조종하는 것(말, 자전거). 유저 위치가 곧 탈것 위치라서 이 설계 범위가 아니다. 필요해지면 따로 설계한다.
- **기준 좌표계**: 좌표를 무엇을 기준으로 쟀는가. `move`는 월드 기준, `ride_move`는 발판 기준이다.

## 결정 1: 배의 위치는 주고받지 않고 각자 계산한다

처음 생각한 방식은 "출발 버튼을 누른 클라이언트가 배 좌표를 계산해 서버에 계속 보내고, 서버가 모두에게 중계한다"였다. 쓰지 않기로 했다.

- 좌표를 계산하는 클라이언트가 사실상 배의 주인이 된다. 서버는 전달만 한다.
- 그 유저가 끊기면 배가 바다 한가운데서 멈춘다.
- 약 10Hz 좌표로는 배가 끊겨 보이고, 배 위 유저와 배의 좌표가 서로 다른 시점에 도착해 유저가 떨린다.

대신 **서버는 사건(출발 시각)만 정하고, 위치는 모든 클라이언트가 같은 공식으로 계산한다.** 항로가 직선이고 걸리는 시간이 정해져 있으므로 출발 시각만 알면 어느 순간의 위치든 나온다.

```csharp
float t = Mathf.Clamp01((ServerNow - start) / duration);
Vector3 pos = Vector3.Lerp(fromBerth.position, toBerth.position, Mathf.SmoothStep(0, 1, t));
```

- 메시지는 출발할 때 한 번만 오간다. 출발시킨 유저가 나가도 배는 계속 간다.
- 늦게 들어온 유저도 현재 배 상태를 받으면 지금 위치를 바로 계산한다.
- 조건: 클라이언트가 서버 시각을 알아야 한다. 접속 때 서버 시각을 받아 내 시계와의 차이(offset)를 저장한다.

서버는 배를 상태 기계로 관리한다. 두 유저가 동시에 출발을 눌러도 서버가 먼저 받은 하나만 받아들이고, 항해 중 요청은 거절한다.

```
정박(정원) ──출발 요청──▶ 항해(정원→섬, start) ──시간 경과──▶ 정박(섬)
정박(섬)   ──출발 요청──▶ 항해(섬→정원, start) ──시간 경과──▶ 정박(정원)
```

정박 지점은 씬의 `21 • Sacred isle/Ferry route/Garden berth`, `Isle berth`다. 배와 형제로 둔다(배의 자식이면 배와 함께 움직여 버린다).

## 결정 2: 배 위의 유저는 배 기준 좌표를 보낸다

배 위 유저가 월드 좌표를 보내면, 다른 화면에서는 부드럽게 움직이는 배보다 그 유저가 늦게 따라와 갑판 위에서 미끄러져 보인다. 그래서 배 위에서는 **발판 id + 발판 기준 로컬 좌표**를 보낸다.

- 보내는 쪽: `platform.transform.InverseTransformPoint(내 위치)`
- 받는 쪽: `platform.transform.TransformPoint(로컬 좌표)` — 유저가 배에 붙어 함께 움직인다.
- 가만히 서 있으면 로컬 좌표가 안 바뀌므로 보낼 것도 없다.

## 결정 3: 탈것마다 메시지를 만들지 않고 id 로 구분한다

`ferry_move`처럼 탈것마다 메시지를 만들면 탈것을 늘릴 때마다 메시지와 DB 를 고쳐야 한다. 그래서 범용 메시지 두 개에 발판 id(문자열)를 적는다.

| 방향 | 메시지 | 필드 |
|---|---|---|
| 클라이언트 → 서버 | `ride_move` | `platform`, `x`, `y`, `z` (로컬) |
| 서버 → 클라이언트 | `player_ride_moved` | `id`, `platform`, `x`, `y`, `z` |
| 서버 → 클라이언트 | `scene_players`/`player_joined`의 플레이어 객체 | `riding: {platform, x, y, z}` 또는 `null` |

- id 는 사람이 읽을 수 있는 고정 문자열(`ferry_willow`). 소문자·숫자·`_` 1~40자.
- 서버: `python/src/dg_village_server/platforms.py`의 `PLATFORMS`(씬별 id 목록). 지금 씬에 없는 id 는 `unknown_platform` 에러로 거절한다.
- 클라이언트: 발판마다 컴포넌트에 `[SerializeField] private string _platformId;`를 두고, 씬 시작 때 `Dictionary<string, …>`에 등록한다. 모르는 id 는 무시한다.
- 발판을 추가할 때는 서버 `PLATFORMS`에 id 한 줄, 클라이언트 오브젝트에 같은 id 만 적으면 된다.
- 내릴 때 메시지는 없다. 다시 `move`를 보내면 서버는 "땅 위"로 판단한다. `change_scene`도 탑승을 푼다.

## 결정 4: DB 는 바꾸지 않는다

- 유저 위치는 지금처럼 마지막 **월드** 좌표만 저장한다. 서버는 `ride_move`로 월드 좌표를 바꾸지 않으므로, 배 위에서 끊기면 타기 직전(선착장 근처) 좌표가 저장된다.
- 탑승 상태와 배 상태는 서버 메모리에만 둔다. 서버가 재시작되면 배는 처음 선착장으로 돌아간다.
- 나중에 탈것 상태를 꼭 저장해야 하면 범용 테이블 하나(`platform_id`, `state` JSON)로 한다.

## 하위 호환

- 옛 클라이언트는 `player_ride_moved`를 모르는 메시지로 보고 경고만 찍는다(`GameSocket.cs`의 `default:`). 배 위 유저는 탄 자리에서 멈춰 보인다. 플레이어 객체의 새 `riding` 필드는 무시한다.
- 새 클라이언트가 옛 서버에 `ride_move`를 보내면 `invalid_message` 에러가 온다. 그런데 지금 클라이언트는 **모든** `error`에서 `JoinFailed`를 호출한다(`GameSocket.cs`의 `case "error":`). 그래서 **서버를 먼저 배포하고 클라이언트를 나중에 릴리스한다.** 가능하면 join 중일 때만 `JoinFailed`를 부르도록 고친다(배와 관계없이 지금도 있는 문제).

## 클라이언트에서 할 일 (네트워크보다 어려운 부분)

- **배 이동**: 배에 `Rigidbody`(Is Kinematic)를 붙이고 `FixedUpdate`에서 `MovePosition`으로 옮긴다.
- **내 캐릭터 태우기**: Rigidbody 가 있어도 자동으로 따라오지 않는다. `PlayerMovement.FixedUpdate`가 매 물리 프레임 수평 속도를 입력값으로 덮어써서 마찰력이 밀어 준 속도가 지워지기 때문이다. 발 아래가 배면 배의 속도(`(이번 위치 - 지난 위치) / Time.fixedDeltaTime`)를 플레이어 속도에 더한다. Dynamic Rigidbody 를 움직이는 부모의 자식으로 넣는 방법은 쓰지 않는다.
- **탔는지 판단**: 발 아래로 Raycast 를 쏘고 맞은 콜라이더에서 `GetComponentInParent<발판 컴포넌트>()`. 발판을 걸어 올라가는 지금 배 구조(`Gangway`)와 맞는다. 같은 검사를 물리(속도 더하기)와 네트워크(`ride_move`) 양쪽에 쓴다.
- **출발·도착**: 출발할 때 `Boarding gate`를 켜고 `Gangway`를 끈다. 도착하면 반대로.
