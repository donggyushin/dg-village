# 서버가 구독을 쥐면 근접 음성은 끝난다

결론부터 말하면 **"가까운 유저끼리만 대화"라는 목표 때문에 RTC를 직접 구현할 필요는 없다.** SFU에서 "누가 누구의 트랙을 받는지(subscription)"를 서버가 정하게 하면 근접 음성이 된다. 이 방식은 P2P mesh 자체 구현보다 **더 강하게** 서버가 규칙을 강제한다. dg-village에 가장 맞는 길은 **LiveKit**이다. 오픈소스 SFU라 직접 호스팅할 수 있고, 같은 프로토콜의 Cloud 버전도 있다. FastAPI 서버가 지금처럼 `Room.hearers()`로 듣는 관계를 계산하고, 바뀐 부분만 LiveKit의 `UpdateSubscriptions` API로 보내면 된다. 미디어 코드(코덱, ICE, 에코 제거)는 한 줄도 직접 쓰지 않으면서 "누가 듣는가"의 결정권은 100% 우리 서버에 남는다. 그러니 사용자가 자체 구현으로 얻고 싶던 제어권은 SDK로도 손해 없이 얻는다. 반대로 진짜 자체 구현(Unity의 `com.unity.webrtc` + P2P mesh)은 **패키지가 2026-08에 deprecated**됐고, 에코 제거가 없으며, WebGL을 지원하지 않는다. 라운지에 사람이 몰리면 mesh가 무너지고 TURN 서버도 따로 돌려야 한다. 솔로 취미 프로젝트로는 현실성이 낮다. 남는 실제 쟁점은 두 가지다. 하나는 **지연**이다. Sydney Lightsail에 SFU를 올리면 한국↔한국 통화가 Sydney를 왕복해서 입에서 귀까지 약 200~250ms가 된다. 다른 하나는 **비용 구조**다. LiveKit Cloud는 접속한 분 단위로 과금하는데, dg-village는 "켜두고 일하는" 게임이라 이 구조와 잘 안 맞는다.

## 동기 검증: 근접 제어는 SFU 구독 API가 서버에서 해준다

사용자가 직접 구현을 원한 이유는 "SDK를 쓰면 근접 규칙을 마음대로 못 하지 않을까"라는 걱정이다. LiveKit은 이 걱정을 정면으로 해결한다. 클라이언트를 `autoSubscribe` 꺼진 상태로 접속시키는 방식은 LiveKit 문서가 직접 **"spatial applications"용으로 권장**한다 ([LiveKit: Subscribing to tracks](https://docs.livekit.io/home/client/tracks/subscribe/)). 이렇게 하면 서버(roomAdmin 권한)가 `UpdateSubscriptions(room, identity, track_sids, subscribe)`로 **특정 참가자가 받을 트랙을 직접 설정**한다 ([LiveKit Server APIs](https://docs.livekit.io/reference/server/server-apis/)). Python 공식 SDK `livekit-api`로 FastAPI에서 바로 호출할 수 있다. 토큰 발급도 `api.AccessToken(...).with_grants(VideoGrants(...))` 한 줄이다 ([LiveKit: Generating tokens](https://docs.livekit.io/home/server/generating-tokens/)).

dg-village의 세 가지 규칙은 모두 "구독 집합"으로 바뀐다. 복도 규칙은 `hearingRadius` 안에 있는 화자만 구독하는 것이다. 라운지 규칙은 같은 carpet 영역 안의 전원을 구독하는 것이다. 책상 포커스 규칙은 그 사람의 모든 구독을 끊고, 동시에 그 사람의 마이크 트랙을 아무도 구독하지 않게 하는 것이다. 포커스 쪽은 서버가 `can_publish`를 회수하는 방법도 있다. 회수하면 **그 참가자의 트랙이 자동으로 unpublish**되므로 "책상에 앉은 내 목소리는 아무에게도 안 간다"를 서버가 보장한다 ([LiveKit: Managing participants](https://docs.livekit.io/home/server/managing-participants/)). 서버는 이미 채팅에 이 판정을 쓰고 있다. 그래서 새로 만들 것은 tick마다 "listener → 들리는 speaker 집합"을 계산해서 **바뀐 부분만** API로 보내는 diff 루프뿐이다.

업계 사례도 같은 구조로 모인다. Kumospace는 공간 오디오를 **Daily의 track subscription API**로 구현했다 ([Daily blog: Kumospace](https://www.daily.co/blog/how-kumospace-built-a-platform-for-meaningful-connection/)). Gather는 전담 팀이 **자체 SFU를 여러 데이터센터에서** 운영한다 ([Gather 채용공고](https://jobs.orbit.mit.edu/companies/gather-2-674309dd-fe8e-47c7-8df5-bcd9b2a88b57/jobs/31180045-staff-backend-engineer-video)). 오픈소스 가상오피스 WorkAdventure는 P2P 버블을 4명으로 제한해 왔는데, v1.27.0(2025-11)부터 **5번째 사람이 오면 LiveKit SFU로 전환**한다 ([WorkAdventure 1.27.0](https://workadventu.re/release/workadventure-1-27-0-the-road-to-workadventure-2/)). 대부분의 서비스가 미디어 전송은 외부 SFU에 맡기고, "누구 트랙을 받을지"만 자기 게임 로직으로 정한다. dg-village의 Desk/Lounge/Hallway는 Gather의 quiet mode/private area/5타일 근접과 거의 1:1로 대응한다 ([NOAA GatherTown Readme](https://esrl.noaa.gov/gmd/publications/annual_meetings/2022/GatherTown%20Readme.pdf)).

보안 측면에서는 오히려 SFU가 낫다. 모두를 구독시키고 클라이언트에서 볼륨만 0으로 내리는 방식은 **조작된 클라이언트가 방 전체를 들을 수 있으므로** 프라이버시가 없다. mesh는 시그널링 서버가 연결 중개를 거부하는 것까지만 할 수 있다. 이미 맺어진 P2P 연결은 서버가 끊을 수 없다. 서버 구독 방식은 미디어 경로 자체를 서버가 정한다. 다만 한 가지는 **아직 검증되지 않았다**. 토큰을 `can_subscribe=false`로 발급해도 admin `UpdateSubscriptions`로 강제 구독이 되는지를 문서에서 확인하지 못했다. 이 조합이 되면 클라이언트가 스스로 구독하는 길이 완전히 막힌다. 안 되면 대안이 있다. `can_subscribe=true`로 두고, 서버 지시에 따라 각 publisher가 `setTrackSubscriptionPermissions`로 허용 대상을 설정한다 ([LiveKit Publishing](https://docs.livekit.io/transport/media/publish/)). 공격자는 듣는 쪽이고 publisher는 자기 프라이버시만 걸려 있으니, 이 정도면 충분하다. 로컬 실험 첫 단계에서 확인할 항목이다.

## 진짜 자체 구현은 Unity 쪽에서 막힌다

P2P mesh를 직접 만들려면 Unity용 WebRTC 바인딩이 필요하다. 그런데 공식 `com.unity.webrtc`는 README에 **"com.unity.webrtc is deprecated."**가 2026-08-18에 추가됐다. 마지막 릴리스는 3.0.0(libwebrtc M116, 2025-09)이다. 요구사항 문서는 Unity 6000.3만 명시하고, **WebGL은 지원하지 않는다** ([GitHub](https://github.com/Unity-Technologies/com.unity.webrtc), [requirements](https://docs.unity3d.com/Packages/com.unity.webrtc@3.0/manual/requirements.html)). 더 치명적인 문제는 **echo cancellation/noise suppression API가 없다**는 점이다. "마이크로 소리가 다시 들어간다"는 이슈 [#964](https://github.com/Unity-Technologies/com.unity.webrtc/issues/964)와 AudioOptions PR [#978](https://github.com/Unity-Technologies/com.unity.webrtc/pull/978)이 수년째 열려 있다. "일하면서 켜두는" 게임은 스피커와 마이크를 동시에 켜는 상황이 기본인데, AEC가 없으면 하울링이 난다. 프로젝트는 6000.6을 쓰고 있어서 더 이상 고쳐지지 않는 패키지가 깨질 위험도 있다.

mesh 구조 자체에도 한계가 있다. 업계에서 보통 말하는 mesh 한계는 영상 기준 **4~6명**이다 ([BlogGeek.me](https://bloggeek.me/webrtcglossary/mesh)). WorkAdventure도 버블을 4명으로 묶었다. 음성만 쓰면 8~10명 정도는 버틸 것으로 보이지만 실측 자료는 없다. 라운지에 15명이 모이면 각자 14개 스트림을 보내고 14개를 받는다. 그리고 범위를 넘나들 때마다 offer/answer + ICE + DTLS 핸드셰이크가 다시 일어난다. 그래서 히스테리시스(R+2에서 연결, R+4에서 해제)로 연결은 유지하고 mute만 토글하는 식의 보정 로직을 직접 짜야 한다. 연결의 약 **10~20%는 TURN relay가 필요**하다는 추정이 있다 ([Metered](https://www.metered.ca/blog/what-is-a-turn-server/), [EasyRTC](https://github.com/gunjank/easyrtc/blob/master/docs/easyrtc_server_ice.md)). 그래서 coturn을 운영하고 임시 자격증명도 발급해야 한다. CrewLink 같은 P2P 근접 음성 사례도 결국 시그널링 서버와 relay를 직접 운영했다 ([Pterodactyl egg: BetterCrewlink Server](https://eggs.pterodactyl.io/egg/games-bettercrewlink-server)). WebGL에서는 브라우저 `RTCPeerConnection`으로 가는 jslib 브리지를 별도로 만들어야 한다. 결국 **데스크톱 경로와 웹 경로를 각각 따로 짜야** 한다.

mediasoup, Janus, Pion 같은 자체 SFU 툴킷은 mesh 문제를 풀어준다. 대신 시그널링, 룸, 인증을 전부 직접 써야 한다(mediasoup은 "signaling agnostic"인 Node.js 모듈이다 — [mediasoup overview](https://mediasoup.org/documentation/overview/)). 공식 Unity SDK도 없다. 반면 LiveKit Unity SDK(`client-sdk-unity`, Rust FFI)는 **v2.1.0(2026-09-23)**까지 활발하게 릴리스되고 있다. 지원 플랫폼은 Windows/macOS/Linux이고, Unity 6000.3.10에서 테스트됐다. v2.1.0에서 **Unity Audio 경로에 AEC3가 추가**됐다 ([README](https://raw.githubusercontent.com/livekit/client-sdk-unity/main/README.md), [releases](https://github.com/livekit/client-sdk-unity/releases)). 원격 오디오가 Unity `AudioSource`로 나오기 때문에, 원격 플레이어 오브젝트에 붙이고 `spatialBlend`로 거리 감쇠와 패닝을 공짜로 얻는다. WebGL용으로는 별도 패키지 `client-sdk-unity-web`이 있다 ([GitHub](https://github.com/livekit/client-sdk-unity-web)). 서버 측 구독 로직이 같으므로 웹에서도 근접 규칙은 그대로 동작한다.

## 상용 SDK 비교: Vivox는 공짜, LiveKit은 서버 권한

| 옵션 | 근접 구현 방식 | 서버 권한 강제 | WebGL | 비용 (10 / 50 / 200 동시접속) | dg-village 적합도 |
|---|---|---|---|---|---|
| **LiveKit** (OSS self-host / Cloud) | 서버가 `UpdateSubscriptions`로 구독 지정 | **완전** (서버가 미디어 경로 결정) | 공식 별도 패키지 | Self-host: VPS 비용만 / Cloud: $50 / ~$155 / $500 | **최적** |
| Vivox (Unity) | positional 채널 + 라운지별 별도 채널 | 클라이언트가 보고한 위치 기반 | **2D 단일 채널만** | $0 / $0 / $0 (5,000 PCU까지 무료) | 데스크톱만이면 차선 |
| ODIN (4Players) | 서버가 위치 기반 culling, 라운지 = 별도 room | 클라이언트 위치 기반 | JS SDK로 따로 | €0 / ~€14.5 / ~€58 | 저렴한 차선 |
| Agora | 클라이언트 spatial audio 엔진 | 클라이언트 | 커뮤니티 베타 플러그인 | ~$61 / ~$347 / ~$1,350+ | 비쌈 |
| Photon Voice 2 | interest group, 클라이언트에서 거리 체크 | 클라이언트 | 공식 미지원 | 20 CCU 무료, 이후 유료 | 네트워크 스택 이중화 |
| Dissonance | Unity 내 grid/collider proximity | 전송 계층에 의존 | 미지원 추정 | ~$110 1회 | UDP 전송 필요, 부적합 |

비용은 "1인당 하루 4시간 접속"이라는 가정 아래 각 공식 가격표로 계산한 값이다. Vivox는 **5,000 PCU까지 무료**다 ([UGS pricing](https://activation.unity3d.com/en/products/gaming-services/pricing)). ODIN은 25 PCU까지 무료, 이후 PCU당 €0.29다 ([ODIN pricing](https://odin.4players.io/pricing/)). LiveKit Cloud는 무료 Build 플랜이 5,000 participant-minute이고, Ship 플랜이 $50/월에 150,000분 포함이며 초과분은 분당 $0.0005다 ([LiveKit pricing](https://livekit.com/pricing)). Agora는 1,000분당 $0.99다 ([Agora pricing](https://docs.agora.io/en/realtime-media/voice/reference/pricing.md)). 핵심은 과금 단위다. 하루 종일 켜두고 대부분 침묵하는 이 게임에는 **PCU 과금(Vivox, ODIN)이 분 과금(LiveKit Cloud, Agora)보다 유리하다.** LiveKit Cloud의 무료 5,000분은 테스터 10명이 하루만 켜둬도 넘는다. 대신 포커스 모드에서 음성 연결을 끊으면 분 과금 비용을 줄이는 수단이 된다.

Vivox는 돈 측면에서 매력적이다. 하지만 세 가지 약점이 있다. 첫째, positional 채널이 **클라이언트가 초당 2~4회 보고하는 위치**로 동작한다 ([Vivox positional](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/positional-channel-configuration)). 둘째, 라운지를 표현하려면 채널을 여러 개 써야 한다. 셋째, **WebGL에서는 3D 채널이 없고 인스턴스당 채널이 하나**뿐이라서 웹 빌드에서는 근접 음성 자체가 안 된다 ([Vivox WebGL](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/vivox-webgl)). ODIN도 서버가 culling을 하지만 좌표는 클라이언트가 보낸다 ([ODIN update_position](https://docs.4players.io/voice/core/api/functions/odin_room_update_position)). 두 서비스 모두 이미 있는 `Room.hearers()` 판정을 쓰지 못하고, 근접 규칙을 벤더 쪽 모델로 한 번 더 표현해야 한다. 그러면 채팅과 음성의 규칙이 어긋날 수 있다. LiveKit은 **채팅과 음성이 같은 함수 하나를 공유**한다는 점에서 구조적으로 앞선다. 또 오픈소스라서 Cloud로 시작해도 같은 코드로 직접 호스팅할 수 있어 벤더 lock-in이 가장 낮다. 회사도 2026-01에 $100M Series C를 받아 당분간 사라질 가능성은 낮다 ([Unite.ai](https://www.unite.ai/livekit-reaches-1-billion-valuation-as-voice-ai-infrastructure-heats-up/)).

## Sydney 서버 한 대의 진짜 문제는 용량이 아니라 지연이다

LiveKit OSS를 기존 Lightsail $12(2 vCPU/2 GB)에 컨테이너 하나로 올리는 것은 용량상 가능해 보인다. LiveKit 벤치마크는 16코어에서 약 96만 pkt/s를 낸다 ([LiveKit Benchmarks](https://docs.livekit.io/transport/self-hosting/benchmark/)). 50명이 각자 10명을 듣고 전원이 말하는 최악의 경우를 계산해도 약 25,000 pkt/s로 한 코어의 일부다(추정치). 다만 burstable CPU이고 FastAPI/Postgres와 같이 돌기 때문에 `lk load-test`로 반드시 확인해야 한다. 트래픽은 Sydney 플랜이 **1.5 TB/월**(다른 리전의 절반)이고 초과분은 **$0.17/GB**다 ([Lightsail data transfer FAQ](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-faq-data-transfer-allowance.html)). Opus DTX(침묵 시 거의 전송 안 함)와 범위 밖 unsubscribe가 있으면 소규모로는 여유가 있다. LiveKit에는 TURN이 내장돼 있어서 coturn이 필요 없다 ([LiveKit self-hosting](https://docs.livekit.io/transport/self-hosting/deployment/)). 단, Caddy가 443을 쓰고 있으므로 TURN/TLS는 5349 포트와 별도 sslip 호스트명으로 돌려야 한다.

문제는 물리적 거리다. 서울↔Sydney RTT는 **약 145ms**다 ([Economize](https://www.economize.cloud/resources/aws/latency/ap-northeast-2-vs-ap-southeast-2/)). 한국 화자 → Sydney SFU → 한국 청자 경로는 네트워크에서만 약 145ms가 든다. 여기에 프레임, jitter buffer, 장치 지연을 더하면 입에서 귀까지 **200~250ms**다. ITU-T G.114의 "자연스러운 대화" 기준인 150ms를 넘고, "가능하지만 말이 겹치는" 구간에 들어간다 ([ITU-T G.114](https://www.cs.columbia.edu/%7Eandreaf/new/documents/other/T-REC-G.114-200305.pdf)). 서울↔도쿄는 약 36ms라서 SFU만 동아시아에 두면 이 문제는 사라진다. 선택지는 세 가지다. 첫째, Sydney에서 감수한다(수다용으로는 충분하다). 둘째, LiveKit Cloud의 edge를 쓴다(지역 목록은 이번 조사에서 확인하지 못했다). 셋째, LiveKit만 서울/도쿄의 저가 VPS로 분리한다. 코드는 셋 다 같고 URL과 키만 다르므로, 지연 문제는 **나중에 결정해도 되는 배포 문제**다.

## 추천 경로와 첫 단계

**추천: LiveKit + 서버 구동 구독.** 처음에는 로컬 `livekit-server --dev`로 만든다. 외부 테스트 단계에서는 Lightsail에 직접 호스팅(추가 비용 0, 약 250ms 지연)한다. 지연이 거슬리면 LiveKit만 동아시아로 옮기거나 Cloud로 바꾼다. 이렇게 하면 "voice는 직접 구현하지 않는다"는 기존 결정을 지키면서도, 사용자가 원한 "우리 서버가 근접을 결정한다"는 제어권을 온전히 얻는다. 미디어 서버까지 직접 운영하니 '자체 호스팅 SFU'라는 의미의 자체 구현이기도 하다.

첫 단계는 다음 순서로 진행한다. 첫째, Docker로 `livekit/livekit-server --dev`를 띄우고, Unity 6000.6에 `client-sdk-unity`를 git URL `#v2.1.0`로 설치해 컴파일되는지 확인한다(공식 테스트 버전은 6000.3이다). 둘째, FastAPI에 `POST /voice/token`을 추가한다(`livekit-api`, identity = 계정 hex id). 셋째, `livekit-server --dev` + `lk` CLI로 **`can_subscribe=false` 토큰에 admin 강제 구독이 되는지**를 실험해서 보안 모델을 확정한다. 넷째, `RoomManager`의 10Hz tick에 "voice graph diff"를 붙인다. 이 diff는 `Room.hearers()`의 결과를 listener별 speaker 집합으로 바꾸고, 바뀐 쌍만 `update_subscriptions`로 일괄 전송한다. 마이크 track SID는 LiveKit webhook이나 `ListParticipants`로 얻는다. 다섯째, Unity에서 `autoSubscribe`를 끄고 Unity Audio 모드로 접속한다. 받은 원격 트랙은 `RemotePlayer`의 `AudioSource`(spatialBlend 1)에 `AudioStream`으로 연결하고, 마이크 on/off 버튼을 HUD에 붙인다. 여섯째, Mac과 Windows에서 **스피커로 AEC3를 테스트**한다(v2.1.0에서 막 들어온 기능이다). 마지막으로 Lightsail 방화벽에 UDP 50000-50200 / TCP 7881 / 5349를 열고, Caddy에 `livekit.` 서브도메인 reverse proxy를 추가한 뒤 `lk load-test`로 2 vCPU 한계를 잰다.

설계상 한 가지 고를 점이 있다. 리서치 노트는 LiveKit 방을 지금처럼 `"<channel>/<map>"` 단위로 만들자고 제안한다. 하지만 구독을 서버가 전부 정하므로 **LiveKit 방을 채널 단위로 하나만** 두고 맵 구분도 hearers 규칙에 맡기는 방법이 있다. 이렇게 하면 포털로 이동할 때 음성 재접속이 사라진다(내 추론이다. 노트에서 검증된 내용은 아니다).

## Conclusion

이 질문의 본질은 "RTC를 직접 만들 것인가"가 아니라 "들을 권리를 누가 정하는가"였다. 그 답은 미디어 계층이 아니라 제어 계층에 있다. dg-village 서버는 이미 그 제어 계층(`Room.hearers()`)을 갖고 있다. 그래서 음성 도입은 새 기술을 만드는 일이 아니라 **기존 판정 결과를 하나 더 내보내는 일**이 된다. 채팅과 음성이 같은 규칙을 공유하면 "채팅은 안 들리는데 음성은 들린다" 같은 불일치가 구조적으로 생기지 않는다. 이것이 Vivox나 ODIN 대신 LiveKit을 고르는 가장 큰 이유다.

남은 리스크는 기술보다 운영 쪽이다. Sydney 고정 리전 때문에 생기는 약 250ms 지연, 분 과금과 "하루 종일 켜두는" 사용 패턴의 충돌, 갓 나온 Unity AEC3의 실제 품질, 그리고 `can_subscribe` 강제 구독 동작이 그것이다. 넷 다 첫 주말 로컬 프로토타입과 테스터 몇 명이면 측정할 수 있다. 측정 결과에 따라 바뀌는 것은 배포 위치와 요금제뿐이고 코드는 그대로다. 그러니 지금 해야 할 결정은 하나, LiveKit으로 프로토타입을 시작하는 것이다.
